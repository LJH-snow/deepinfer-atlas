把优化放回执行路径

本页讨论两类浪费：设备等 CPU，以及验证了很可能被拒绝的候选。前者由异步调度减少空隙，后者由 DSpark 的置信度调度分配验证计算。两者相互配合，但不是同一种优化，也不保证在所有负载下都更快。

以下图形都是解释性示意，格子宽度不代表测量时间，示例预算不代表默认配置。本项目没有运行 GPU / NPU 推理或复测官方基准。

01 / CPU 与设备的异步调度

解决的问题：设备算完，还要等 CPU

同步路径中，CPU 先选批次，设备执行 forward / sample；CPU 等到结果后做输出后处理，再准备下一批。后处理和下一次调度期间，设备可能空闲。官方称异步批次调度为 ZOS（Zero-overhead Scheduling），目标是把这些 CPU 工作与设备计算重叠。

官方文档 D05官方异步调度说明↗ 源码 E13Worker.execute_model_step↗

核心过程：先发计算，再消费上一轮输出

  1. LLMEngine.step() 先调用 C++ Scheduler 选批次，再下发 execute_model_step。
  2. Worker 先启动当前步主模型 forward；ModelRunner 的 forward 和 sample 方法都用 forbid_cuda_sync() 约束内部同步。
  3. 随后 Worker 才调用 _post_process_step(prev_step_state)。这个边界会等待上一轮 sampling event；等待和后处理发生在本轮 forward 已经启动之后。
  4. 启动当前步采样并记录 event。ZOS decode 保存当前状态，留给下一轮后处理；prefill 或关闭 ZOS 时在本轮处理。
  5. 生成循环结束时 flush_inflight_reqs() 排空尚未处理的输出。

为什么元数据还要修正

提前调度时，CPU 还没有上一轮完整采样结果。Worker 的 _correct_seqlens_qk() 根据上一轮设备上的 accepted token 数和 draft 信息修正长度。启用变长验证时，还在 GPU 端用新置信度重新分配 query 长度，并回写 pinned buffer（固定在主存、便于异步传输的缓冲区）。这使“先调度”与“使用正确的实际长度”能衔接起来。

源码 E28Worker._correct_seqlens_qk↗ 源码 E27compute_seqlens_q_by_confidence_rates↗

适用条件与解释范围：NORMAL / COMPLETION 类型默认设置 ZOS，显式 DEEPINFER_ZERO_OVERHEAD_SCHEDULING=0 可覆盖。这里核对了 Python/C++ 主路径，没有模拟所有多 rank、NPU 后端或抢占组合。源码方法名含 CUDA / GPU 时按原名引用，不据此声称所有后端内部完全相同。

02 / DSpark：把验证预算用在更有希望的候选上

解决的问题：生成草稿不等于值得全部验证

推测解码（speculative decoding）先生成多个 draft token，再由主模型验证。若所有请求都固定验证同样长的草稿，就可能把计算花在低接受概率的位置。官方称 DSpark 的方案使用 Confidence Head 预测接受概率，再据硬件性能曲线分配验证预算。当前代码的 draft 模块入口类名为 DFlash；两种名称处于方案与实现的不同层次。

官方文档 D04官方 DSpark 描述↗ 源码 E25ConfidenceHead↗ 源码 E26DFlash.sample_drafts / run_drafts↗
  1. 1. 生成下一轮草稿DFlash 输出 draft IDs 与各位置置信度。
  2. 2. 选择总预算C++ 结合历史预测与时间估计，选择 total_q。
  3. 3. 分配验证长度ZOS 使用设备上的新置信度修正每条 seqlen_q。
  4. 4. 实际验证后输出Sampler 决定接受的 token，并生成再下一轮草稿。

这是跨轮循环的解释性简化。这里的顺序不能理解为每次 Python step 都依次拿到了当轮全部 CPU 结果。

源码中的关键过程

置信度 ≠ 验证结果
ConfidenceHead 输出各候选位置的估计接受概率。process_MTPInfo() 将它们累乘成前缀预测接受率并保留历史。主模型的实际验证仍由 Sampler 执行，不能用高置信度绕过验证。

CPU 决定总预算
MTPVarlen.schedule() 对候选的预测收益排序，比较“预期有效 token 数 / 估计 forward 与 sampler 时间”。代码用 N−2 轮的预测接受率决定预算，以保持时序约束；没有 decode 性能曲线时回退到现有 draft 长度。这里选择的是 query token 总量，不是一个对所有请求相同的固定草稿长度。

还有哪些值得继续读

SWA（Sliding Window Attention，滑动窗口注意力）的 bounded replay 只保留有界后缀以减少 decoder 侧 prefill 工作；保留长度必须覆盖窗口与最大回退长度。官方说明和 ModelRunner 的条件检查可作为下一入口。底层 attention、矩阵乘和专家通信则分别从 FlashMLA、DeepGEMM、DeepEP 的接入点进入。

性能描述应该怎样验证

本图谱只给出机制和可核查入口，不提供“已复测加速比”。上游 README 的 prefill / decode 图说明了所用 SM100 数量，并给出 sweep 脚本；官方 Q&A 的动态验证表则有自身并发与并行配置。若引用这些数字，必须连同各自测试条件引用，不能把一种配置的收益作为本机或任意部署的承诺。

要做自己的实验，先固定本页的 commit、模型 checkpoint、硬件拓扑、并发和长度分布，再分别切换 ZOS、varlen 等配置。保留运行日志、吞吐与延迟分布后，才能讨论收益。继续沿优化路线读源码。
