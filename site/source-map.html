路线 A / 先走通一次离线请求

  1. 从 examples/offline_inference.py 开始

    为什么读：知道真实调用者交给引擎什么。关注：create_llm、输入准备、generate、decode 与 close，及最外层 launch_dp。下一步：跟进 generate，而不是先钻模型每一层。

    源码 E01main → LLM.generate↗
  2. 读 LLM.generate → _add_request

    为什么读：看见文本如何变成请求。关注：tokenizer、采样参数复制、请求 ID 和 add_request。下一步：找到引擎把 Sequence 放进队列的位置。

    源码 E02LLM.generate↗ 源码 E03LLM._add_request↗ 源码 E05LLMEngine.add_request / _enqueue↗
  3. 读 LLM._run_engine → LLMEngine.step

    为什么读：理解生成是循环而非一次模型调用。关注：unfinished、step、flush、clone 和最终排序。下一步：跟 step 里的 scheduler.schedule 和 execute_model_step。

    源码 E04LLM._run_engine↗ 源码 E06LLMEngine.step↗ 源码 E07LLMEngine._execute_model_async_step / post_process↗
  4. 用输出路径把环闭合

    为什么读：区分候选、已接受 token 和返回对象。关注：process_MTPInfo、process_outputs、build_request_outputs、_check_stop。下一步：回到调用者确认它拿到的是 token 对象列表还是可选解码文本。

    源码 E20LLMEngine._process_model_outputs↗ 源码 E21Scheduler._check_stop↗ 源码 E04LLM._run_engine↗

  2. BlockManager → CacheEngine

    为什么读：分开“块编号生命周期”和“设备张量布局”。关注：引用计数、pin/free、gpu_blocks、state blocks、GPUCacheInterface。下一步：在 ModelRunner 中观察缓存如何传给模型。不要在这里寻找完整长期缓存服务。

    源码 E11BlockManager↗ 源码 E12CacheEngine.do_allocate_kv_cache↗ 源码 E37LLMEngine 初始化缓存管理与调度器↗
  3. Worker.execute_model_step → ModelRunner

    为什么读：找到实际 launch 和同步的位置。关注：当前 forward、上一轮后处理、当前 sample、event 与 prev_step_state；以及 graph replay 和直接调用的分支。下一步：沿 self.model / self.model.sample 到执行层。

    源码 E31prefill_attn_varlen_sparse / decode_mla_mqa_sparse↗ 源码 E32bf16_gemm↗ 源码 E30UserBuffer 的依赖↗ 源码 E33gather / cp_broadcast↗ 源码 E36WorkerBase.run_workers↗

阅读时保留这几个区分

文件夹名字不等于一个运行时组件
model_executor/ 是执行实现所在包；不能据其名称画出一个未经确认的 ModelExecutor 类。
支持能力不等于默认开启
nextn、varlen、batch-invariant、确定性采样各有自己的条件。先看示例与配置，再分析选中分支。
模块名或注释不等于服务已经交付
CacheEngine 的旧类说明提到 CPU cache / swapping；结论要以当前实际分配实现和官方发布范围为准。
不确定时回到证据，而不是填补内部细节
没有运行模型的结论标为静态核对；完整服务的未公开组件只引用官方说明。
